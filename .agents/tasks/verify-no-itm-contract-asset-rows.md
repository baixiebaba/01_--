# 坏账校验 SQL：T20/T10 均无合同资产时的输出调查

## 总结结论

在“**T20 和 T10 都没有合同资产，但至少有一侧仍有应收账款或其他应收款数据**”这一场景下，两个当前脚本都会输出合同资产行，并将 `AMT_20`、`AMT_10` 和 `AMT_DIFF` 按 0 处理。合同资产行不是由合同资产事实数据驱动，而是由静态 `ITM` 维度与已出现的公司/客商维度交叉生成。

因此，针对原问题“如果 T20 和 T10 都没有合同资产，是否仍有合同资产对应的行”，答案是：**会，只要该公司（汇总 SQL）或该公司+客商组合（客商级明细 SQL）已在 T20/T10 的其他科目中出现。**

但有一个边界：如果指定范围内 T20 和 T10 完全没有任何三类科目数据（不只是没有合同资产），当前两个脚本都不会凭空生成公司/客商维度，也就不会输出合同资产行。当前维度只从事实 CTE 反推公司或客商，没有直接从 `$Entity.code` 建立公司种子维度。

## 证据

### 1. ITM 是静态的三行科目维度

两个文件的 `ITM` CTE 都固定定义了三类：应收账款（`SEQ = 1`）、其他应收款（`SEQ = 2`）和合同资产（`SEQ = 3`），其中合同资产映射为 `CONTO20 = '1460000000'`、`CONTO10 = '1460000000'`。

- 汇总 SQL：`01_代码/02_DWM/C_应收应付/坏账校验query.sql`，`ITM` CTE
- 客商级明细 SQL：`01_代码/02_DWM/C_应收应付/坏账校验query_客商级明细.sql`，`ITM` CTE

所以 `ITM` 中的合同资产值并不要求合同资产源数据存在才出现；它是查询自身定义的维度行。

### 2. T20/T10 的 LEFT JOIN 只负责给事实行映射科目，不会在事实为空时造行

汇总 SQL 中：

- `T20` 从 `TGK_FIMA_DEV.AW_MR9_ARPM02_000001` 取数，并通过 `LEFT JOIN ITM I ON I.CONTO20 = A.COD_CONTO` 映射 `ITEM_SEQ/ITEM_NAME`；随后按公司和 ITM 维度聚合。
- `T10` 从 `TGK_GB_HISENSE.ZTAB_AG_TF_OC` 取数，并通过 `LEFT JOIN ITM I ON I.CONTO10 = T.HKONT` 映射；随后按公司和 ITM 维度聚合。

客商级明细 SQL 结构相同，只是额外按客商聚合：

- `T20` 按公司、ITM、`NVL(LTRIM(A.CUST_CODE, '0'), '(NO_CUST)')` 聚合。
- `T10` 按公司、ITM、`NVL(LTRIM(T.CVCODE, '0'), '(NO_CUST)')` 聚合。

这些 `LEFT JOIN` 不会在合同资产事实不存在时产生 `ITEM_SEQ = 3` 的事实行；合同资产行的生成发生在后续的 `RESULT_DIM`，而不是 T20/T10。

### 3. 汇总 SQL 的统一维度包含合同资产 ITM

文件：`01_代码/02_DWM/C_应收应付/坏账校验query.sql`

- `COMPANY_DIM` CTE 对 `T20` 和 `T10` 的 `COMPANY_CODE` 做并集：
  - `SELECT COMPANY_CODE FROM T20`
  - `UNION`
  - `SELECT COMPANY_CODE FROM T10`
- `RESULT_DIM` CTE 使用：`FROM COMPANY_DIM C CROSS JOIN ITM I`。

因此，只要某公司在 T20 或 T10 的任意纳入科目中出现，`RESULT_DIM` 就会为该公司生成 ITM 的三行，其中必然包括 `ITEM_SEQ = 3 / ITEM_NAME = '合同资产'`。这里不要求合同资产在 T20 或 T10 中有事实数据。

最终查询从 `RESULT_DIM D` 出发，分别 `LEFT JOIN T20` 和 `LEFT JOIN T10`，连接键是公司加 `ITEM_SEQ`。对合同资产缺失的一侧（本题中为两侧）使用：

- `NVL(T20.AMT_20, 0)`
- `NVL(T10.AMT_10, 0)`
- `NVL(T20.AMT_20, 0) - NVL(T10.AMT_10, 0)`

所以结果中的合同资产行会是公司、合同资产、`0、0、0`。

### 4. 客商级明细 SQL 的统一维度也包含合同资产 ITM

文件：`01_代码/02_DWM/C_应收应付/坏账校验query_客商级明细.sql`

- `CUST_DIM` 将 T20 和 T10 的 `COMPANY_CODE、CUST_CODE、CUST_NAME` 合并，再按公司和客商去重。
- `RESULT_DIM` 使用：`FROM CUST_DIM C CROSS JOIN ITM I`。

因此，只要某公司+客商组合在 T20 或 T10 的任意纳入科目中出现，该组合就会生成 ITM 三行，包括合同资产行。合同资产不存在时，最终按公司、ITM、客商连接 T20/T10 均匹配不到合同资产事实，金额字段通过 `NVL` 输出 0。

该 SQL 的客商规则还会把空客商编码统一为 `'(NO_CUST)'`，因此如果其他科目的事实行使用空客商，合同资产的零金额行也会以 `'(NO_CUST)'` 这一客商组合输出。`CUST_NAME` 来自 `CUST_DIM` 中已有事实侧客商名称；不存在合同资产事实本身不会提供合同资产专属客商名称。

### 5. 当前逻辑并非直接使用 FULL JOIN，但结果目的等价于补齐缺失侧

两个脚本的最终查询都是以人工构造的 `RESULT_DIM` 为主表，再对 T20/T10 做两个 `LEFT JOIN`。因此它不依赖 FULL JOIN 来发现合同资产行：

1. T20/T10 提供已出现的公司或公司+客商组合；
2. `CROSS JOIN ITM` 补齐三类科目维度；
3. 两侧事实金额分别左连接；
4. `NVL(..., 0)` 将缺失事实转换成 0。

在本题场景下，这种结构能够保留合同资产行，且避免直接对两侧事实做 FULL JOIN 时可能出现的粒度膨胀。

## 分别回答两个脚本的结果

### 汇总 SQL

若 T20/T10 都没有合同资产、但公司在应收账款或其他应收款至少一侧存在：会输出该公司的合同资产行，结果为：

- `ITEM_NAME = '合同资产'`
- `AMT_20 = 0`
- `AMT_10 = 0`
- `AMT_DIFF = 0`

若 T20/T10 对该公司完全没有三类科目数据，则 `COMPANY_DIM` 没有该公司，`RESULT_DIM` 不会生成该公司的任何行。

### 客商级明细 SQL

若 T20/T10 都没有合同资产、但某公司+客商组合在应收账款或其他应收款至少一侧存在：会输出该公司+客商的合同资产行，金额同样为 `0、0、0`。

若 T20/T10 完全没有任何三类科目数据，则 `CUST_DIM` 为空，`RESULT_DIM` 为空，不会输出合同资产行。若只有其他科目存在，则合同资产行的客商集合取自其他科目在两侧出现的客商并集。

## 结论与建议

- 对用户提出的正常场景（T20/T10 没有合同资产，但还有其他坏账校验科目数据），**当前修复后的两个脚本都会输出合同资产行**；统一维度包含静态 ITM 中的合同资产值，不是只有合同资产数据存在时才有 ITM 行。
- 因此该场景无需再把 T20/T10 事实连接直接改成 FULL JOIN；当前 `COMPANY_DIM/CUST_DIM + RESULT_DIM CROSS JOIN ITM + LEFT JOIN + NVL` 已实现缺失合同资产按 0 展示。
- 如果业务还要求“即使三类科目在 T20/T10 都完全没有数据，也必须按选择的实体输出三类行”，当前脚本仍不满足。最小修复方向是：在汇总 SQL 的 `COMPANY_DIM` 中增加由 `$Entity.code` 形成的实体种子集合；客商级明细则还需要一个明确的客商主数据/实体客商种子集合，再与 `ITM` 交叉连接。仅把事实表连接改成 FULL JOIN 不能解决“事实两侧都为空时没有维度键”的问题。

本次仅读取并分析 SQL，未修改两个业务 SQL 文件。
