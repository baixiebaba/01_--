# CPM_SP_S2S_TDAYS_M 设计审查

## 审查范围与结论

本审查以用户原始要求为权威，核对了：

- 设计文档：`.agents/tasks/CPM_SP_S2S_TDAYS_M-design.md`
- 参考过程：`01_代码/02_DWM/C_应收应付/CPM_SP_M2M_ARP_TOV_M_PHASE2.sql`
- 同目录 ARP 程序和校验 SQL
- 知识库副本：`98_临时存/kbdata_副本.json`
- 用户提供的配置字段、目标字段、HIE 推导规则、10 组限制、6 个公式

**Verdict：CHANGES_REQUESTED。** 当前设计已经覆盖了动态 SQL 安全、同表读写隔离、18 个金额聚合、6 个天数公式和异常处理的主要方向，但仍有阻塞性契约没有闭合。它可以作为实现方案草稿，不能据此产出可部署的 Oracle 第一版。

## Findings

1. **HIGH — 用户指定目标对象与知识库对象冲突，设计没有完成对象身份决策。**
   - **位置：** 设计 Summary、§3.2 部署矩阵、Implementation Step 1、待确认假设 1。
   - **问题：** 用户要求的目标是 `AW_MR7_ARPA01_000001`，但知识库登记的是 `AW_MR7_ARPS02_000001`（“应收周转展示表”），且本地没有前者的 DDL、SQL 或台账记录。设计只是把差异列为“待确认”，同时继续以 ARPA01 作为目标白名单和 39 列 INSERT 的前提；因此 owner、真实列、是否新建对象以及是否应使用 ARPS02 都没有确定，代码无法安全编译或部署。
   - **具体修复：** 获取业务/DBA 的权威对象确认并二选一：若 ARPA01 是新目标，补充其完整 DDL、台账和 owner；若 ARPA01 是笔误或别名，修订配置、设计和 INSERT 为 ARPS02。未完成前，目标白名单、删除和 INSERT 必须阻断，而不是仅在运行时“校验不存在后报错”。

2. **HIGH — 配置表、source 白名单、GTT、日志表和直接授权没有可执行的部署契约。**
   - **位置：** 设计§3.2~§3.3、§3.6~§3.7、Implementation Steps 1~2。
   - **问题：** 设计要求固定 owner、RULE_ID、对象类型、列长度、权限和两个 GTT，但没有给出任何实际值或完整 DDL。知识库也没有 `AW_RUL_TOVCAL_000001`、`SESSION_TOVCAL_RESULT`、`SESSION_TOVCAL_SCOPE`、用户指定目标表或 `V_REF_ED_D_GRAN_CAL` 的登记。尤其 GTT 只描述“包括哪些列”，未冻结每个维度的长度、索引列、唯一约束和 owner；这不足以让实现者写出可编译、可授权的过程。
   - **具体修复：** 在设计中附上部署矩阵和 DDL 摘要：`OWNER.OBJECT`、对象类型、完整列定义、非空/默认值、索引、GTT `ON COMMIT`、日志列长度、过程 `AUTHID` 以及每项直接 grant。将这些资料作为代码生成前硬门禁；缺失时不得声称“第一版可执行”。

3. **HIGH — “动态 target”与实际方案互相矛盾，source 也没有实际白名单条目。**
   - **位置：** Summary、§3.2、§5、Implementation Steps 7~9。
   - **问题：** Summary 表述为按配置指定的动态 `TARGET_TABLE` 装载，但§5又规定目标名不能直接来自配置、必须来自 target 白名单映射；当前映射没有任何实际 target 条目。`SOURCE_TABLE` 虽允许动态读取，设计却假定所有合法 source 都共享同一套 18 个金额及基础字段，未给出 source 列契约或条目。配置若出现第二个 target 或一个列名不同的 source，设计既没有明确拒绝点，也没有映射方案。
   - **具体修复：** 明确 v1 的范围。推荐固定只支持已确认的一个 target，并在读取配置时 `TARGET_TABLE` 不等于该 canonical 名立即报错；为每个允许 source 列出 owner、对象类型、18 个金额、基础维度、数据类型和可过滤列。若确实要支持多个 target/source，建立逐对象映射矩阵和逐目标 INSERT 契约，不能用“动态白名单”代替实际内容。

4. **HIGH — 配置运行范围与参考程序的公司/事业部范围语义不一致，未证明哪一个是本引擎口径。**
   - **位置：** 设计§1 的 SESSION_AZIENDA_LIST 初始化、§2 的 `P_BG` 规则、§5 的公司交集谓词、Out of Scope。
   - **问题：** 参考过程实际不只读取 `V_REF_AZIENDA`：它还通过有效期、`AW_RUL_ATSMAP_000001`、`AW_RUL_COSMAP_000001`、`AW_RUL_DWMCRS_000001` 和锁定规则限制公司及事业部。设计改为仅按 `V_REF_AZIENDA HIE='10'` 和参数匹配，并明确不继承 AR 规则，但没有证据说明新 S2S 引擎应使用“全部组织层级”而不是现有有效周转范围。这样 `ALL` 可能读取/删除参考过程不会处理的公司，`P_BG` 也可能与有效周转事业部口径不一致。
   - **具体修复：** 在设计中明确并固定一个选择：要么复用已存在的周转公司/事业部范围（逐表、有效期、锁定规则列出），要么明确声明 v1 的授权范围就是 `V_REF_AZIENDA HIE=10` 的 ELEM，并提供业务批准和 `2600/6100/ALL` 的期望结果表。scope、来源谓词和 DELETE 必须使用同一个范围定义。

5. **HIGH — HIE 引用对象无法从现有证据落地，特别是 `V_REF_ED_D_GRAN_CAL` 未登记。**
   - **位置：** 设计§4 HIE 映射、§5 固定 SQL、SQL/DDL 校验清单、验收标准 7。
   - **问题：** 用户规则要求 `COD_DEST2 -> V_REF_DEST2`、`D_GRAN_CAL -> V_REF_ED_D_GRAN_CAL`。知识库仅能证明多个 owner 下有 `V_REF_DEST2` 类登记，不能证明批准 owner、列类型或权限；`V_REF_ED_D_GRAN_CAL` 没有登记结果。设计要求运行时校验，但并未提供映射矩阵，因此实现者仍可能选错同名对象或在缺失时才发现无法编译/执行。
   - **具体修复：** 增加固定矩阵 `(来源列, HIE 对象 owner.name, 对象类型, ELEM/HIE/NODE 类型及长度, 直接 grant)`，至少闭合两个用户示例。构建 scope/执行任何来源 SQL 前验证矩阵对象；缺失、列类型不兼容或权限不足直接失败，不能按名称猜测或回退到其他 owner。

6. **HIGH — 目标独占性未证实，通配维度下的 DELETE 仍可能覆盖其他生产数据。**
   - **位置：** 设计§7、§8、待确认假设 10、验收标准 12。
   - **问题：** 设计的删除键包含场景、期间和 11 个目标维度，但没有过程归属列；类别和币种刻意不进 scope，会删除该 scope 下全部类别和币种。若目标表还有其他来源、其他引擎或人工数据，当前设计没有办法区分。设计虽写“取得独占证明后启用”，但 Summary 和 Implementation Steps 仍把删除作为正常实现路径，不能称为可执行第一版。
   - **具体修复：** 取得台账/DBA 的独占证明并把它作为部署前硬门禁；否则补充稳定的过程归属键（例如正式审计/来源列）并将其纳入 DELETE、唯一键和 INSERT。为 `ALL/ZZZZ/NULL/空格` 的每个维度提供具体删除样例，证明不会越界。

7. **HIGH — 18 个金额的 source 字段契约没有逐 source 闭合，动态 source 不能仅靠字段名假设。**
   - **位置：** 设计§3.3、§5 固定聚合 SQL、§6、验收标准 9。
   - **问题：** 设计要求 source 必须存在 `COD_SCENARIO`、`COD_PERIODO`、`COD_AZIENDA`、`COD_CATEGORIA`、`COD_VALUTA` 和 18 个金额，但没有给出任何 source 的真实字段清单，也没有说明不同 source 如何把“本月占用金额”映射到可用字段。只在 `ALL_TAB_COLUMNS` 中检查同名列不足以证明业务语义正确；目标表作为 source 时也必须确认它的金额含义和重跑语义。
   - **具体修复：** 为每个 source 白名单条目列出 18 个金额和 5 个基础字段的精确映射、类型/精度、空值处理和场景期间语义；任何缺列或语义未确认的 source 在配置校验阶段拒绝。若 v1 只支持同名列，明确写成固定 source contract，而不是称为通用动态 source。

8. **HIGH — YTD 公式的“本月占用”字段和零分母结果仍是发布阻断假设。**
   - **位置：** 设计§6、Implementation Step 9、待确认假设 7~8、验收标准 9。
   - **问题：** 用户公式写的是“本月占用金额”，用户给出的目标字段没有 `*_MTD_OCP_AMT`；设计自行选择 `*_END_OCP_AMT`，并自行暂选分母为零返回 `0`。这两个选择会直接改变六个天数结果，且“暂选”不能产出可确认的第一版。
   - **具体修复：** 在代码前由业务确认三套（计划/实际/同期）YTD 的本月占用究竟是 END、其他 source 字段还是不存在；同时确认分母为 0 是 `0`、`NULL` 还是业务错误。把确认结果写成唯一字段映射表和三组边界样例，删除“实现者可替换”的表述。

9. **MEDIUM — `COD_CATEGORIA` 和 `COD_VALUTA` 的空值处理改写了用户的“直接对应”规则。**
   - **位置：** 设计§5 固定聚合 SQL、§7、验收标准 10。
   - **问题：** 用户目标资料对 `COD_CATEGORIA`、`COD_VALUTA` 标注的是“直接对应”，只对配置生成的目标维度明确“为空则放 ZZZZ”。设计却把来源类别和币种的 NULL/空格也统一改成 `ZZZZ`。这会使空值来源与真实 `ZZZZ` 来源合并，并改变直接对应的结果；现有参考过程对币种也有固定 CNY/来源逻辑，不能自动证明新目标应采用 ZZZZ。
   - **具体修复：** 明确按目标资料保留 NULL/空格，或由业务正式确认“直接对应但空值归 ZZZZ”。将同一表达式同步用于 result 聚合、目标 INSERT 和验证样例；不要把配置维度的 ZZZZ 规则扩展到类别/币种。

10. **MEDIUM — 配置维度把字面量 `ALL` 当成通配符是新增语义，原始要求没有授权。**
    - **位置：** 设计§2 的 11 个目标维度规范化和删除规则、§7 `NORMALIZE`、验收标准 4/10。
    - **问题：** 用户明确说明的是空值时放 `ZZZZ`，并只明确了参数 `P_AZIENDA/P_BG` 的 `ALL`；没有说明配置中的 `D_BG`、科目、利润中心等字段写 `ALL` 时应展开。设计将所有目标配置字段的 `ALL` 解释成 ZZZZ/通配，可能把合法业务编码或错误配置静默变成跨范围数据。
    - **具体修复：** 二选一并写入配置契约：配置字段只允许 NULL/空格表示通配，`ALL` 作为非法值；或逐字段声明 `ALL` 的含义、输出值、来源范围和 DELETE 语义。未确认前禁止统一按 ALL 处理。

11. **HIGH — 日志失败策略与过程返回语义无法同时满足，且没有“可观测告警”实现。**
    - **位置：** 设计§8 异常顺序、§9、验收标准 15。
    - **问题：** 设计要求日志自治提交、日志失败不阻断主流程，并规定 END 日志在业务 COMMIT 后失败时仍返回成功但要“监控可见”。过程签名没有 OUT 状态、告警表、事件接口或返回码；`DBMS_OUTPUT` 也不能作为调度监控契约。另一方面，错误日志失败时也没有规定是否记录备用位置。实现者无法产生可验证的“可观测告警”。
    - **具体修复：** 固定一种可执行策略：推荐把 BEGIN/阶段/ERROR 日志写入失败视为部署错误并在业务提交前失败，END 日志失败则写入已定义的备用告警表/事件并返回明确状态；或者为过程增加正式 OUT/返回码和监控表。将“日志失败不阻断但必须可见”改成具体对象、字段、事务和验收规则。

12. **HIGH — `DBMS_LOCK.ALLOCATE_UNIQUE` 的事务副作用没有纳入事务设计验证。**
    - **位置：** 设计§8 锁、Implementation Step 6、异常顺序。
    - **问题：** 设计要求目标删除/装载到最后才提交，但把 `ALLOCATE_UNIQUE` 放在同一过程事务中，且没有规定该 API 的分配/提交行为、调用时点或验证方法。若分配操作产生提交，前面配置、会话表或 GTT 清理的事务边界会被改变；设计当前的“单主事务”保证就不成立。
    - **具体修复：** 在设计中冻结锁 API 的事务契约：在任何业务 DML 前完成可提交的 lock handle 分配，或预生成/持久化 lock handle；随后只调用 `REQUEST/RELEASE`。用事务哨兵测试证明配置暂存、目标 DELETE、目标 INSERT 的提交点，再允许进入代码生成。

13. **MEDIUM — 共享会话范围表仅按 `SESSION_ID`，没有防止同一数据库 session 重入。**
    - **位置：** 设计§1 初始化/清理、§8 GTT 与事务边界。
    - **问题：** `SESSION_AZIENDA_LIST` 和 `SESSION_V_REF_AZIENDA` 的清理、写入和读取都只使用 `SESSION_ID`；设计为 result/scope 增加了 `RUN_ID`，但没有为这两个共享表增加 run 隔离，也没有禁止同一 session 的嵌套/重入调用。第二次调用可以清空第一次调用正在使用的公司范围，导致来源和 DELETE 范围错乱。
   - **具体修复：** 若能改表，给两个共享表增加 `RUN_ID` 并所有 SQL 使用 `(SESSION_ID,RUN_ID)`；若不能改表，在过程开始用 session 级互斥/状态标记拒绝重入，并在验收中覆盖同一 session 重入。

14. **MEDIUM — bind 名称由 RULE_ID 拼接但没有长度和唯一性上限。**
    - **位置：** 设计§4、§5、Implementation Step 7。
    - **问题：** 设计要求绑定名包含规则标识和组号，例如 `B_R123_G02_I1001`，但没有限制 RULE_ID 的长度、字符集或不同规则哈希碰撞。配置主键来自未提供的真实 DDL；过长或非法 bind 名可能导致 `DBMS_SQL.PARSE/BIND_VARIABLE` 失败，碰撞则可能绑定错误值。
    - **具体修复：** 将 bind 名固定为长度受限的安全编码，例如 `B_` + 固定长度十六进制哈希 + `G##` + `I####`，对同一 SQL 生成结果做唯一性检查；RULE_ID 只作为日志字段，不直接进入标识符。

15. **MEDIUM — 场景格式被设计擅自收紧，可能拒绝合法项目场景。**
    - **位置：** 设计§1 参数校验。
    - **问题：** 用户只提供了目标 `COD_SCENARIO VARCHAR2(15)` 和参数名，没有给出“4 位年份 + 大写字母/数字/下划线”的正则。设计用该正则和小写拒绝规则作为硬校验，可能拒绝项目已有的合法场景编码；同时 `V_YEARMONTH` 又依赖前四位，缺少真实场景编码契约。
    - **具体修复：** 从配置/调度/DDL 获取正式场景格式；若没有正式格式，v1 只校验非空、长度和用于 `YYYYMM` 的前四位为合法年份，不自行禁止其他字符。将场景格式测试样例写入验收。

16. **MEDIUM — `LISTAGG` 生成日志公司范围存在溢出路径。**
    - **位置：** 设计§1、§9、参考过程沿用的 `V_AZIENDA` 设计。
    - **问题：** 设计允许 `P_AZIENDA='ALL'` 展开全部公司，并用 `LISTAGG` 组成最多 4000 字符的日志值；公司集合可能超过 4000 字节，Oracle 会在日志前抛出 `ORA-01489`，使合法运行失败。该路径也没有说明多字节字符长度策略。
    - **具体修复：** 日志不再承载完整公司清单，改为记录原始参数、公司数量和 `RUN_ID`；如必须展示清单，使用明确版本支持的截断语义并记录“已截断”，不能让日志字段长度决定业务执行结果。

## Verified Assumptions

1. 参考 Oracle 过程 `CPM_SP_M2M_ARP_TOV_M_PHASE2` 的签名顺序确实是 `P_SCENARIO、P_PERIODO、P_AZIENDA、P_BG、SESSION_USER`。
2. 参考过程确实读取 `SYS_CONTEXT('USERENV','SESSIONID')`，清理并填充 `SESSION_AZIENDA_LIST`、`SESSION_V_REF_AZIENDA`，并向 `ZTAB_CPM_LOG` 写入 BEGIN、阶段、END 和 ERROR；异常路径执行 `ROLLBACK`、记录错误、`COMMIT`、`RAISE`。
3. 参考过程的公司范围不是单纯的 `V_REF_AZIENDA`：其 SQL 同时使用有效期、`AW_RUL_ATSMAP_000001`、`AW_RUL_COSMAP_000001`、`AW_RUL_DWMCRS_000001` 等规则。设计选择不继承这些规则属于新方案决策，不是参考程序已经证明的事实。
4. 用户原始资料明确列出了 `COLUMN_NAME_1~10`、`COLUMN_FILTER_1~10`、`COLUMN_VALUE_1~10` 共 10 组字段，并给出了 `COD_DEST2 -> V_REF_DEST2`、`D_GRAN_CAL -> V_REF_ED_D_GRAN_CAL` 的 HIE 推导示例。
5. 当前设计文本确实列举了 9 类规则（`=、<>、IN、LIKE、NOT LIKE、HIE、NOT IN、IS NULL、IS NOT NULL`），并规定了 IN/NOT IN 分块、括号和绑定值不拼接的方向。
6. 当前设计明确了先将 source 结果写入 GTT、所有 source 完成后才删除/装载 target；也明确了 18 个金额先聚合，再计算 6 个天数，且包含同表读写路径。
7. 知识库副本登记了 `AW_MR9_ARPM03_000001`、`AW_MR8_ARPS01_000001` 和 `AW_MR7_ARPS02_000001` 等 ARP 对象，但没有登记用户指定的 ARPA01、TOVCAL 配置表、目标过程或 `V_REF_ED_D_GRAN_CAL`。

## Unverified/Wrong Assumptions

1. **未验证：** `AW_MR7_ARPA01_000001` 的 owner、真实 DDL、39 列完整性、非空/默认列、目标独占性和是否替代知识库中的 ARPS02。
2. **未验证：** `AW_RUL_TOVCAL_000001` 的 owner、列类型/长度、稳定 RULE_ID、有效期类型和重叠规则；设计只是假定支持字符型 `YYYYMM`。
3. **未验证：** 所有合法 source 都有设计要求的同名 18 个金额和基础维度，且过滤列全部是字符类型。
4. **未验证：** `V_REF_DEST2` 和 `V_REF_ED_D_GRAN_CAL` 的批准 owner、存在性、对象类型、`ELEM/HIE/NODE` 列结构、长度、字符集和直接权限。
