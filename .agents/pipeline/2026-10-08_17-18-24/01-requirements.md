# 坏账计算存储过程核对与修复需求

## Summary

对照应收数据模型详细设计文档中的三个工作表：`ARPM02-坏账计算表-STEP1坏账计提基数`、`ARPM02-坏账计算表-STEP2坏账计算`、`ARPM02-坏账计算表-STEP3坏账分摊`，逐字段、逐步骤检查存储过程 `02_DWM/C_应收应付/CPM_SP_M2M_ARP_BD_M_PHASE2.sql`。核对范围包括过滤条件、关联条件及关联粒度、计提基数、`FORM_DATI` 比例、个别认定调整、正负坏账处理、上月期末坏账、核销、账龄分摊（`AGE_ALLOC`）、坏账金额（`BD_AFAL`）、本月坏账发生额（`MTD_BD_PROV_OCUR`）以及结果写回逻辑。仅对已确认与设计文档不一致或会造成错误的 SQL 进行修复，实际保存 SQL 修改，不创建 Git commit。

假设：
- Excel 工作表中的字段定义、处理步骤、公式和示例值是本次核对的业务基准；若文档存在同一规则的冲突，以同一工作表的明确字段/公式说明为准，并在最终报告中标明冲突。
- “逐字段逐步骤核对”要求覆盖三个工作表出现的输入字段、计算字段、输出字段和关键条件；不要求修改设计文档。
- 可执行的本地验证以静态、结构和可用的 SQL 语法检查为限；没有 Oracle 环境时不得声称 SQL 已在 Oracle 执行通过。
- “最新修改记录置顶”按现有 SQL 文件头的记录格式追加本次修改记录，不重排或改写无关历史记录。

## Functional Requirements

1. **结构化读取设计文档**
   - 使用 `openpyxl` 或本地 XML 方式读取指定 Excel，不以人工目视或非结构化截图作为唯一依据。
   - 定位并读取三个指定 sheet，保留足以追溯字段、步骤、公式、过滤条件、关联关系和输出写回规则的原始内容。
   - 若 sheet 缺失、读取失败或关键区域无法解析，应明确记录为阻塞/未验证项，不得据此臆造 SQL 修改。

2. **STEP1 坏账计提基数核对**
   - 核对计提基数的来源字段、数据范围、过滤条件、关联表、关联键和关联粒度。
   - 核对正数和负数金额、核销数据、上月期末坏账及个别认定调整是否按设计参与或排除计提基数计算。
   - 核对 SQL 输出字段与设计字段的映射、聚合粒度、空值和重复关联风险；发现确认的问题时修复 SQL。

3. **STEP2 坏账计算核对**
   - 核对 `FORM_DATI` 比例的取值来源、匹配条件、适用账龄/分类、比例计算及空值或无匹配时的行为。
   - 核对普通计提与个别认定调整的计算顺序、金额符号、正数坏账和负数坏账的处理规则。
   - 核对上月期末坏账、核销及本期基数在坏账计算中的使用，确认计算结果与设计公式一致。
   - 核对 `BD_AFAL` 和 `MTD_BD_PROV_OCUR` 的公式、符号、舍入/汇总位置及字段写回，修复已确认错误。

4. **STEP3 坏账分摊核对**
   - 核对账龄分摊 `AGE_ALLOC` 的来源、分摊顺序、分摊比例/金额、剩余金额处理和金额符号。
   - 核对分摊结果是否按设计维度写回，特别是客户、组织、科目、账龄或其他文档规定维度的关联粒度。
   - 核对分摊汇总后与 STEP2 计算结果的勾稽关系，避免重复分摊、金额丢失或多对多放大。

5. **SQL 修复边界与风格**
   - 仅修改能够由设计文档或静态分析确认的问题；不得为“可能更好”而重构无关逻辑或格式化无关代码。
   - 遵循项目 Oracle SQL 风格：关键字、函数和对象名大写；保留/补充中文业务注释；在文件头将最新修改记录置顶。
   - 修改必须直接保存到指定存储过程文件，不修改 Excel、其他 SQL 或无关文件，不创建 Git commit。

6. **验证与报告**
   - 对修改前后关键字段、条件、公式、关联粒度和写回路径形成可追溯核对记录。
   - 运行可用的本地静态、结构或 SQL 语法验证，并记录实际命令及结果。
   - 最终报告必须列出：关键业务规则、发现的问题及设计依据、具体修改、变更文件、验证命令及结果、无法验证的项目和 Oracle 连接限制。

## Non-Functional Requirements

- **可追溯性：** 每项 SQL 修改应能对应到具体 sheet、步骤、字段/公式或关联规则；无法建立依据的内容不得修改。
- **最小变更：** 保持原有过程接口、执行顺序和无关逻辑不变，避免引入未经需求要求的依赖。
- **一致性：** SQL 修改应保持现有 Oracle 存储过程语法和项目命名、注释及大小写风格。
- **可验证性：** 核对过程和验证结果应可由后续设计/实现步骤复查，明确区分已验证、静态推断和因缺少 Oracle 环境未验证的内容。

## Acceptance Criteria

1. 三个指定 sheet 均已使用 `openpyxl` 或本地 XML 结构化读取；读取结果覆盖各 sheet 的字段、公式/规则、过滤、关联和写回信息，且异常情况已记录。
2. STEP1、STEP2、STEP3 均有逐字段逐步骤核对结果，至少明确说明计提基数、`FORM_DATI`、个别认定、正负坏账、上月期末坏账、核销、`AGE_ALLOC`、`BD_AFAL`、`MTD_BD_PROV_OCUR` 和关联粒度的设计规则与 SQL 实现是否一致。
3. 每个确认的问题都能指出设计文档依据和 SQL 位置；仅确认存在问题的内容被修改，未确认的问题不被臆改。
4. 修复后的 SQL 已实际保存至 `02_DWM/C_应收应付/CPM_SP_M2M_ARP_BD_M_PHASE2.sql`，文件头包含置顶的最新修改记录，且未产生无关文件修改或 Git commit。
5. 修复后不存在已确认的过滤遗漏、错误关联粒度/多对多放大、公式错误、金额符号错误、错误写回或 STEP2 与 STEP3 分摊不一致问题；关键汇总结果满足设计文档规定的勾稽关系。
6. 已运行所有可用的本地静态/结构/语法验证，并在最终报告中准确列出命令、结果和限制；若无法连接 Oracle，明确声明未进行 Oracle 执行验证，不伪造通过结果。
7. 最终报告完整列出关键规则、问题及依据、具体修复、变更文件、验证结果和未验证项，足以供设计评审和后续实现验收。

## Out of Scope

- 不修改或补录 Excel 设计文档，不改变其业务口径。
- 不修改 `CPM_SP_M2M_ARP_BD_M_PHASE2.sql` 之外的 SQL、表结构、索引、数据、调度配置或 Oracle 参数，除非后续明确提出并单独评审。
- 不新增业务规则、字段或接口，不进行与三个指定 sheet 无关的性能重构、代码格式化或清理。
- 不执行生产数据修复、生产部署或 Git commit；不在缺少 Oracle 连接时声称完成数据库运行验证。
