# 按场景期间公司回写投保金额与未覆盖比例

该过程以 `P_SCENARIO`、规范化后的 `P_PERIODO` 和 `P_AZIENDA` 限定 `AW_MR6_ARPINS_000001` 的更新范围，再按公司+客商汇总 `AW_MR9_ARPM02_000001` 的 AR 账龄并换算投保金额。`MTD_END_RATE` 采用账龄币种期末汇率除以投保币种期末汇率，同币种直接取 1；之后按保障天数选择账龄段并计算未覆盖比例。**likely** 的主要风险是汇率缺失和非法保障天数会静默产生 NULL 结果，而不是阻止批次完成；**possible** 的数据前提是同一公司+客商只有一个账龄币种以及目标表支持 ROWID。

Watch for: **likely** 缺失汇率会使 `MTD_END_RATE`、本位币投保金额和免赔额变为 NULL；**confirmed** `INS_COV_DAYS` 不在 30、60–90、120–180、360 时会使账龄余额及未覆盖比例为 NULL；**possible** 混币账龄被 `MAX(COD_VALUTA)` 压成一个币种，必须由数据约束保证。

**Verdict**: NEEDS_CHANGES

## High-level view

目标行和 AR 账龄源都限制在当前场景、期间和参数公司，AR 源按公司+客商且 `LE_AGE_FLAG = 'AR'` 聚合；MERGE 没有插入分支，因此不会扩大写入范围。汇率和币种选择仍依赖“每个公司+客商只有一个账龄币种、每个币种只有一个有效期末汇率”的数据前提。

正常数据下，30、60–90、120–180、360 分别累计 BCY_0、BCY_0~1、BCY_0~2、BCY_0~3，B=0 的两个分支也与文档公式一致。**confirmed** 区间外天数没有兜底，**likely** 缺失汇率没有失败/告警闭环。

ROWID MERGE 的源侧连接键当前被两个聚合保证为单行，未见明显的 Oracle 多匹配问题。**possible** 目标对象若不是支持物理 ROWID 的堆表，则该实现不能编译或执行。

1. **缺失汇率的静默结果（likely）** — 缺失或为零的期末汇率会写入 NULL 的 MTD_END_RATE、本位币投保金额和免赔额，且批次仍成功提交；在 MERGE 前校验并失败/告警，或明确允许 NULL 的业务语义。
2. **无 AR 匹配与 B=0 混淆（likely）** — 无账龄匹配被置为零余额，但金额换算仍为 NULL，和汇率缺失组合时未覆盖比例可能变成 1；区分真实零余额、缺少匹配和缺少汇率后再套公式。
3. **保障天数缺口无兜底（confirmed）** — NULL、31–59、91–119、181–359 等值会使账龄余额和未覆盖比例为 NULL；校验输入域或定义这些区间的归属。
4. **公司+客商混币取 MAX（possible）** — 同一分组存在多个账龄币种时，MAX(COD_VALUTA) 不能代表汇总金额；约束单一币种或改为按币种处理。
5. **ROWID 对象类型前提（possible）** — IOT、视图等无物理 ROWID 的目标对象会导致编译/执行失败；在目标 schema 核实表类型并检查每个源 ROWID 唯一。
6. **缺少 Oracle 运行验证（confirmed）** — 当前环境没有目标库或 sqlplus，无法验证编译、字段精度和异常数据行为；上线前在目标 schema 编译并执行边界/异常组合测试。

## Details

### 当前批次的目标行边界与 AR 账龄拓扑

`CALC_BASE` 同时限定目标表的场景、期间和参数公司，`AGING_SUM` 对源表使用相同限制；`P_AZIENDA` 通过逗号包围后的精确匹配支持单公司、公司列表和 `ALL`。最终只有 `WHEN MATCHED THEN UPDATE`，所以不会插入或更新范围外记录。该结论为 **confirmed**，对应目标筛选 131–138 行和 MERGE 更新 197–206 行。

`AGING_SUM` 明确筛选 `LE_AGE_FLAG = 'AR'`，按 `COD_AZIENDA, CUST_CODE` 分组，并对 `BCY_0_AMT` 至 `BCY_3_AMT` 分别 `SUM(NVL(..., 0))`；`CALC_BASE` 仅按公司+客商连接。这一部分为 **confirmed** 符合用户要求，也意味着同公司同客商的不同科目、利润中心或其他 AR 明细会合并进同一个 B。

**possible** 风险在 `MAX(A.COD_VALUTA)`：如果同一公司+客商的 AR 明细存在多个币种，金额虽仍被汇总，但 MAX 选出的币种不能代表混合币种金额的统一折算币种。应以数据约束或核对 SQL 保证该分组只有一个非空 `COD_VALUTA`，否则需按币种分别处理或明确折算口径。

### MTD_END_RATE 与本位币金额换算

**confirmed** 正常匹配路径的公式是 `A_RATE.CAMBIO_FINALE / I_RATE.CAMBIO_FINALE`；投保币种与账龄币种相同且两者非空时取 1。投保金额和免赔额分别乘以该比率，逐项对应文档中的 `BCY_INS_AMT` 和 `BCY_INS_DDBL_AMT`。`RATE_LIST` 按币种取 `MAX(CAMBIO_FINALE)`，因此也依赖同场景期间同币种只有一个有效汇率的前提。

**likely** 缺失汇率没有被识别为错误：投保币种汇率为空或为 0，或账龄币种汇率为空时，`MTD_END_RATE`、两个本位币金额都会是 NULL，但过程仍提交并记录“更新完成”。如果汇率不完整属于数据错误，必须在 MERGE 前失败/告警；如果业务允许暂缺，则需明确 NULL 的下游含义。

无 AR 匹配时，BCY_0~3 被写为 0，但没有账龄币种可供换算，`MTD_END_RATE` 和本位币投保金额仍为 NULL。把无 AR 余额视为 B=0 是 **likely** 的业务假设，只有文档允许本位币字段为空时才可接受；否则需要区分真实零余额和缺少匹配/缺少汇率。

### 保障天数、B=0 与 INS_UNCOV_RATIO

代码使用 `AGE_BALANCE` 作为 B、`BCY_INS_AMT` 作为 A、`INS_CLM_RATIO` 作为 R、`BCY_INS_DDBL_AMT` 作为 D。**confirmed** 当 A>B 且 B>0 时为 `(B * (1-R) + D) / B`，当 A≤B 且 B>0 时为 `1 - (A-D) * R / B`；B=0 时分别取 0 和 1，避免除零。`BETWEEN` 包含 60、90、120、180 边界，30 和 360 为精确匹配。

**confirmed** 的边界缺口是 `INS_COV_DAYS` 为 NULL、31–59、91–119 或 181–359 时，`AGE_BALANCE` 没有 ELSE 值而为 NULL，`INS_UNCOV_RATIO` 通常也为 NULL。若数据域严格保证只有四类值，这可作为 **likely** 输入约束；若保障天数可自由录入，则必须增加合法值校验或定义缺口区间归属。

**likely** 的组合风险是：汇率缺失使 A 为 NULL、无 AR 匹配使 B 为 0 时，`A > B` 为未知，代码会落入 B=0 的 1 分支，得到 `INS_UNCOV_RATIO = 1`。这会把缺失投保金额混同为全额未覆盖；应先阻断缺失汇率，或在公式前将缺失 A/D 作为数据错误处理。

### ROWID MERGE 的 Oracle 部署前提

`CALC_BASE` 读取 `I.ROWID`，最终以 `T.ROWID = S.TARGET_ROWID` 回写同一目标表。`AGING_SUM` 由公司+客商唯一，`RATE_LIST` 由币种唯一，目标表每个 ROWID 也只出现一次，因此从当前代码形状看没有 **likely** 的 `ORA-30926` 多源匹配问题；同一语句读写目标表也没有单独的明显语义错误。

**possible** 部署风险是 ROWID 不是通用表接口：若 `AW_MR6_ARPINS_000001` 是 IOT、视图或其他不提供物理 ROWID 的对象，`I.ROWID` 会在编译或执行时失败。普通堆表且源结果保持每个 `TARGET_ROWID` 单行时可以接受，但上线前应核实对象类型，并检查源结果 ROWID 唯一性。

### 运行验证缺口

**confirmed** 当前环境没有 Oracle `sqlplus` 或目标库连接，无法验证过程编译、字段类型/精度、目标对象是否支持 ROWID，也无法执行汇率缺失、混币、无 AR 匹配和保障天数边界数据。上线前需要在目标 schema 编译，并用这些异常组合核对预期的阻断、NULL 或默认值行为。
