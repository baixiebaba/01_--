# Post-load reclassification and group-scope enrichment for AR/AP aging facts

The procedure now loads the AR/AP aging fact table and then recalculates legal-entity, management-entity, and management-branch reclassification flags through a post-load `MERGE`. It derives BS and ZTSO04 windows from the inserted rows, calls `F_APAR_REC` with flag `1` for reclassification status and flag `2` for the resulting class, maps that class back to `ACCT_REC_CODE`, and classifies company/counterparty relationships through `V_APAR_ELEM_NODE_TAB`. **Watch for:** **confirmed** ZTSO04 rows pass `TA` to a function with no `TA` branch; **confirmed** their null head code collapses the window across all such rows in a company; **confirmed** missing node mappings default to `GEX`; **likely** the function receives the head code where its existing callers and parameter contract use the effective customer code.

**Verdict**: NEEDS_CHANGES

## High-level view

The post-load merge is keyed by generated `OID` and limited to the newly loaded batch. **Confirmed:** the BS/ZTSO04 predicates do not preserve the effective customer for M01 rows, and `TA` is not a supported function system, so the intended ZTSO04 reclassification path produces no usable flags.

The function call uses the documented `1`/`2` flag pair, and its class-to-account dictionary is represented in the update. **Confirmed:** `ACCT_REC_CODE` is driven only by the legal-entity flag, leaving rows classified only at ME/MB scope unchanged.

The node CTE reduces each element to one mapping before joining company and counterparty. **Likely:** multiple valid mappings are silently discarded; **confirmed:** absent or null mappings are treated as external rather than unknown.

<summary>Details</summary>

### ZTSO04 reclassification is unreachable through the current system mapping

The M01 branch emits `SRC_DETAIL` as `ZTSO04_CK`/`ZTSO04_TH`, sets `SYSTEM_SRC` to `TA`, and leaves `CUST_HEAD_CODE` null (lines 329-381). The ME/MB branches therefore call `F_APAR_REC`, but `TARGET_FACT` derives `MANDT` as `TA`; the workspace copy of `F_APAR_REC` has branches for 600, 610, 680, 700, 800B, 810, 880, 800, and 900, with no `TA` branch. **Confirmed:** those calls return null from the shown function body, so `ME_AGE_FLAG`, `IS_REC_ME`, `MB_AGE_FLAG`, and `IS_REC_MB` remain null for ZTSO04 rows rather than reflecting the requested classification. Either supply the intended SAP client mapping for M01 or exclude it from the function calls and define an explicit classification rule.

### The ME/MB windows combine all M01 customers with a null head key

Both ME and MB partition by `SYSTEM_SRC`, `COD_AZIENDA`, and `CUST_HEAD_CODE`, with MB adding `COD_DEST2` (lines 599-622). In the M01 projection, `CUST_CODE` is populated from `T.CUST_CODE` while `CUST_HEAD_CODE` is always null. **Confirmed:** all ZTSO04 rows for one system/company share the same null customer partition; MB further splits only by profit center. If the intended aging unit is the effective customer (as the DWD contract defines `CUST_CODE`), this over-aggregates balances and sends a company-wide amount into `F_APAR_REC` for every M01 row. The window key must use the requested business key explicitly, with a null policy for M01 rather than relying on a null head-code partition.

### Function customer parameter differs from the established customer key

The merge passes `F.CUST_HEAD_CODE` as `P_CVCODE` (lines 627-694). The function contract names the fifth parameter `P_CVCODE`, the legacy `ETL_HI_DATA_APARAGI.sql` calls it with `T3.CVCODE`, and the DWD output defines `CUST_CODE` as the effective branch-or-head customer while retaining `CUST_HEAD_CODE` separately. **Likely:** special customer rules in `F_APAR_REC`—for example the 2300 customer exception and the 800/900 customer ranges—will not match when a branch exists, because the head identifier is passed instead of the effective customer identifier. Pass the field that the business function calls “customer” (`CUST_CODE`, or an explicitly normalized equivalent), unless the deployed function has been deliberately changed to use head customers and that contract is documented. The `P_FLAG='1'`/`'2'` assignments themselves match the function comment and the existing aging ETL calls; the deployed database signature still needs runtime confirmation.

### ME/MB results do not drive ACCT_REC_CODE

The update maps `ACCT_REC_CODE` exclusively from `S.LE_AGE_FLAG` (lines 748-761). **Confirmed:** a ZTSO04 row cannot get a reclassified account from its ME/MB result, even if the `TA` system mapping is fixed; rows with only ME/MB eligibility retain the inserted `1122000000`. The class dictionary itself matches the function legend (`AR`, `OR`, `AS`, `CA`, `RF`, `AP`, `OP`, `AC`, `CL`, `A9`, `A10`), so the defect is the scope used to select the class, not the listed account targets. Define which scope owns the single `ACCT_REC_CODE` column and apply that scope consistently, including ZTSO04.

### Missing node mappings fail open to GEX

The final scope expression returns `SUB` only when both node and HQ match, `GIN` when HQ matches, and `GEX` for every other case (lines 731-735). **Confirmed:** a missing company row, missing counterparty row, or null `HQ` comparison falls through to `GEX`; rows whose `COD_AZI_CTP` is null are therefore labeled external even though no relationship was established. Add explicit null/unknown handling before the equality tests and decide whether unmapped rows should be null, an `UNK` value, or a rejected data-quality condition. The current expression is not a safe representation of “external.”

### Node de-duplication is deterministic but not demonstrably semantically safe

`NODE_MAP` partitions only by scenario, period, and `ELEM`, then chooses one row by preferring non-null `NODES`, followed by the lexical node and HQ order (lines 703-722). **Likely:** if the view legitimately contains one element in multiple HQ/node relationships, the CTE discards all but one relationship before `SUB`/`GIN`/`GEX` evaluation; the selected relationship is an ordering artifact, not a business-priority rule. The worktree's `草稿/V_APAR_ELEM_NODE_TAB.sql` is empty and does not define the view's uniqueness or meaning, so this cannot be fully verified locally. Validate the view's intended key and either aggregate/qualify it by an explicit hierarchy rule or add a duplicate/missing-mapping data-quality check before merging.

### System-client normalization may bypass supported function branches

`MANDT` is derived only by removing the leading `S` from `SYSTEM_SRC` (lines 575-580). **Likely:** this loses source distinctions such as the `800B` and `680` branches present in the workspace function if those distinctions are encoded in the source data rather than in `SYSTEM_SRC`; all `S800` rows become `800`, and any such rows receive the wrong rule set. The DWD scripts expose only coarse `S800`/`S600` system labels, so the actual deployment encoding cannot be verified from this workspace. Confirm the source-to-client mapping for every supported function branch and preserve the distinction before calling the function.
