# D2M/M2M 应收过程的 CTE 精简与投保更新行为审查

本次工作将 D2M 的标准事实集合和金额窗口计算内联，并将 ARPM02 的维度选择、当前金额聚合、币种明细和历史维度选择压缩到更少的 CTE；同时工作区新增了投保更新过程。D2M 的过滤条件、窗口分区键和 HITACHI 元素集合在结构上保持一致，但窗口表达式新增的 `NVL` 改变了全 NULL 金额分区的函数输入。ARPM02 的内联没有改变业务键、优先级、连接键或 `LISTAGG` 排序；INS 文件在 `main` 基线中不存在，因此无法证明所谓 `AGING_SUM/CALC_BASE` 相对于 Git 基线的等价性，只能审查当前实现。**Watch for:** **confirmed（中）** D2M 全 NULL 金额会从 NULL 变为 0 并可能改变账龄标识；**likely（中）** INS 不同币种时允许账龄汇率为 0，可能把无效汇率折算成 0；**confirmed（中）** INS 未覆盖的保障天数会静默产生 NULL；**possible（中）** INS 按公司+客商取 `MAX(COD_VALUTA)` 依赖单币种数据前提。

**Verdict**: NEEDS_CHANGES

## High-level view

D2M 删除 `STANDARD_FACT` 只是把同一个 `UNION ALL` 放入 `AGG_FACT`，而 `HITACHI_ELEM` 也保留了 `DISTINCT` 和原过滤条件。`TARGET_FACT` 的窗口分区仍对应原 `CUST_KEY = CUST_HEAD_CODE`，但当前行 597、600–627 的 `NVL` 不是单纯内联，需恢复原 NULL 语义或明确接受该业务变化。

ARPM02 的 `CURRENT_DIM_RN/CURRENT_DIM`、`CURRENT_AGG/CURRENT_CURRENCY` 和 `DIM_RN/DIM_SELECTED` 均在原业务键上完成相同的去重、聚合和优先级选择；当前 `LISTAGG` 仍按账龄标识、本位币余额排序。**possible（中）** 同一改动还向 ARPM02 装载增加了 OID 和审计字段，需确认目标表契约，否则会把 CTE 精简之外的部署风险带入本次变更。

INS 当前按每个投保目标 OID 生成一行，AR 账龄按公司+客商聚合，换汇后再按保障天数计算未覆盖比例。**likely（中）** 缺失汇率会以 NULL 字段提交而非失败，且账龄汇率为 0 会走有效折算分支；**confirmed（中）** 仅 30、60–90、120–180、360 有账龄余额定义，其他天数会得到 NULL。

### D2M 标准事实与重分类窗口

`AGG_FACT` 当前直接消费一个括号内的 `DWD_STANDARD UNION ALL M01_FACT`，与被删除的 `STANDARD_FACT` 具有相同输入行集和聚合键。这个 CTE 删除本身不改变装载行粒度。

`TARGET_FACT` 仍筛选相同场景、期间、公司、来源和 `SRC_DETAIL`，并把原 `AMOUNT_FACT` 的三个窗口放在同一层。原窗口的分区使用 `F.CUST_KEY`，而 `TARGET_FACT` 中该别名就是 `A.CUST_HEAD_CODE`；当前分区列因此保持一致。`NODE_MAP` 中的内联集合仍为 `SELECT DISTINCT R.ELEM`，并保留场景、期间、HIE='30'、NODE='1730' 条件，所以 HITACHI 集合的连接基数保持为每个元素最多一行。

**confirmed（中）** 的实际差异在 NULL：基线 `SUM(CASE ... THEN F.BCY_0_AMT ELSE 0 END)` 在匹配行全部为 NULL 时返回 NULL，当前 `SUM(CASE ... THEN NVL(A.BCY_0_AMT, 0) ELSE 0 END)` 返回 0。随后 `REC_FLAG_FACT` 将这个值传入 `F_APAR_REC`（当前行 725 及其调用处），这可能改变 `IS_REC_LG`、`LE_AGE_FLAG`、`IS_REC_ME`、`ME_AGE_FLAG`、`IS_REC_MB` 或 `MB_AGE_FLAG`，因此不能将该变化归为 CTE 内联的等价重写。

### ARPM02 的当前维度、聚合与历史优先级

`CURRENT_DIM` 的内层窗口仍按 `COD_AZIENDA, COD_CONTO, CUST_CODE, COD_DEST2` 分区，先取 `SRC_DETAIL LIKE 'ORG%'`，再按 `OID` 排序；外层仍只保留 `RN=1`。将 `CURRENT_DIM_RN` 放入 `CURRENT_DIM` 没有增加或减少候选行。

`CURRENT_AGG` 现在同时产出金额字段和 `CURRENCY_ACCT_DETAIL`。它们都来自同一个 `CURRENT_SOURCE`，仍按四个业务键分组，`LISTAGG` 的表达式、分隔符和 `WITHIN GROUP (ORDER BY S.LE_AGE_FLAG, S.BCY_0_AMT)` 保持不变；从两个聚合再左连接改成一个聚合，不会重复或丢失当前键。

`DIM_CANDIDATE` 之后的内联窗口仍按相同四个键分区、仅按 `PRIORITY` 升序取一行，等价于原 `DIM_RN` 再 `DIM_SELECTED`。当前内层 `SELECT D.*` 多带了内部 `RN`，但 `RESULT_BASE` 只引用维度业务列，RN 没有进入目标结果或连接条件。由于原逻辑同样只按 `PRIORITY` 排序，同优先级候选的非确定性没有因内联改变。

**possible（中）** 的附带变化是 ARPM02 的 INSERT 不再只装业务字段：当前新增了 OID 及三个审计字段。该变化不改变四键结果粒度，但目标表若没有对应列、列顺序与过程列表不匹配，过程将无法按预期装载；当前工作区没有该目标表 DDL，无法进一步确认。

### INS 投保金额、账龄余额与汇率分支

`CPM_SP_M2M_ARP_INS_M_PHASE2.sql` 在 `main` 中没有同路径文件，Git 基线对该过程是“无文件”，所以不存在可逐行对照的 `AGING_SUM` 或 `CALC_BASE`。当前实现的 AR 聚合粒度是公司+客商，`SUM(NVL(BCY_0_AMT...BCY_3_AMT,0))` 将源 NULL 余额归零；投保侧按目标 OID 保持一行，`RATE_LIST` 按币种聚合后也保持每个币种一行，当前 MERGE 源的连接形状不会因这些聚合产生明显的一对多扩张。

对有有效汇率的不同币种，当前公式是账龄币种期末汇率除以投保币种期末汇率；同币种且两种币种代码非 NULL 时直接返回 1。投保金额和免赔额分别乘以该比率。投保金额、免赔额或赔付比例为 NULL 时，未覆盖比例的前置判断返回 NULL；无 AR 匹配时账龄余额列被置 0，但由于没有账龄币种，换算金额通常为 NULL，前置判断会保留 NULL，而不是把该情况误算成 B=0 的比例 1。

**likely（中）** 的换汇缺口在于不同币种路径：投保币种汇率缺失或为 0 时被排除，账龄币种汇率只检查非 NULL，不检查非 0。因而账龄汇率为 0 会产生 0 比率；若 0 是无效/缺失标志，结果会把投保本位币金额写成 0，并可能改变未覆盖比例。缺失汇率的 NULL 结果也没有阻断批次，只有在业务明确允许 NULL 时才可接受。

`AGE_BALANCE` 对 30、360、60–90、120–180 分别累计 BCY_0、BCY_0~3、BCY_0~1、BCY_0~2，B=0 时未覆盖比例按 A>B 与否分别取 0 或 1。**confirmed（中）** 的边界缺口是 CASE 没有覆盖其他天数或 NULL，因此这些输入无法得到业务公式的 B。另有 **possible（中）** 的数据约束：公司+客商分组的账龄金额如果包含多个 `COD_VALUTA`，`MAX` 只选出字典序最大的币种，不能代表混合币种金额。
