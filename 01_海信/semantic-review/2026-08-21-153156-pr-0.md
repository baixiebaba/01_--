# Revenue account channel-L3 alignment with presum rules

The two revenue-account SQLs attempt to apply the `dwd_fi_mr_gp_presum_mi.sql` priority: sinking fixed customers first, China-region e-commerce mapping where available, then the MDG customer channel. `dwd_fi_mr_rev_acct_mi.sql` preserves that order and uses the same company/customer constants, but its MDG lookup is not reduced to one row per customer. In `dwd_fi_mr_rev_acct_pa_mi.sql`, both SMS and GSMS fixed-customer branches are unreachable, so the added CASE logic always returns the existing MDG channel. No obvious CASE/END or punctuation error was found, and the new PA expressions are derivable from the existing GROUP BY keys.

Watch for: **High, confirmed** — the MI MDG join can multiply aggregated revenue rows because neither side is explicitly unique on the normalized join key; **Medium, confirmed** — all new SMS/GSMS sinking-customer branches are dead code.

**Verdict**: NEEDS_CHANGES

## High-level view

The MI path checks the three fixed customer rules before `ecom_map`, and its online/offline expression matches the published `onoffline_code`. The e-commerce lookup is one row per code, while the following SAP-to-MDG path has no equivalent cardinality bound and can change monetary row multiplicity before insert.

The PA path has no derived sinking code. SMS emits only `020_ON_001` or `020_OFF_001`, and GSMS is fixed to `020_OFF_001`, yet both branches require `020_ON_003`; none of the fixed company/customer mappings can execute. The GROUP BY keys cover the values used by these CASE expressions, so the defect is behavioral rather than an obvious grouping syntax failure.

## MI's e-commerce lookup is bounded, but its MDG fallback is not

**High, confirmed:** The fallback joins `yt_detail.final_customer_code` to `(LTRIM(kunnr,0), zkunnr_mdg)` without selecting one MDG customer per normalized `kunnr`, then joins the customer dimension without reducing it to one row per `cust_code` (`dwd_fi_mr_rev_acct_mi.sql:375-378`). Because `yt_detail` is already aggregated, duplicate KNA1 records—or raw customer keys that collapse to the same value after `LTRIM`—can duplicate the aggregated amounts in the final insert. The reference bounds both stages by grouping KNA1 by customer and the customer dimension by MDG customer (`dwd_fi_mr_gp_presum_mi.sql:173-182`).

The minimal fix is to group by the normalized KNA1 key and choose one `zkunnr_mdg`, then group the needed dimension attributes by `cust_code` or apply a documented unique/current-row filter. If conflicting KNA1 mappings are possible, a deterministic current-record rule is safer than an arbitrary `MAX`.

The `ecom_map` subquery already groups by `ecom_code`, so `channel_segment = ecom_code` adds at most one mapping row per revenue row (`dwd_fi_mr_rev_acct_mi.sql:380-388`). Its CASE branch follows the three fixed-customer branches, and the fixed company/customer sets match the reference. Including `118A`, `118B`, and `1181` explicitly is equivalent to the reference's earlier normalization of those codes to `1180`.

## SMS and GSMS never enter the sinking-customer rules

**Medium, confirmed:** In SMS, every fixed-customer predicate compares `CASE WHEN sms.yw_scope = '电商部' THEN '020_ON_001' ELSE '020_OFF_001' END` with `020_ON_003` (`dwd_fi_mr_rev_acct_pa_mi.sql:103-130`). Neither possible value matches, so `channel_l3_code` and `channel_l3_name` always fall through to `dim_customer_base_info_dd.com_3rd_*`. The company sets, customer IDs, result codes, names, and ordering match the reference but have no effect.

GSMS repeats the unreachable structure with the constant predicate `'020_OFF_001' = '020_ON_003'` (`dwd_fi_mr_rev_acct_pa_mi.sql:384-411`). If PA is not meant to identify sinking transactions, the minimal fix is to remove these dead WHEN branches and retain the direct MDG fallback. If it is meant to align behaviorally with presum, derive an equivalent `sinking_onoffline_code` from the model/customer sinking rules first; changing the comparison to `020_ON_001` would incorrectly classify ordinary online-public rows as sinking.
